# Data model design

A spec says what the business needs; a data model says how the system will hold it. Doing this deliberately, before services are written, is where most downstream defects are prevented: money stored as floating point, status as free text, personal data with no protection, no audit trail, and no way to answer "which rule needed this column?".

The output is one JSON file, `data-model.json`, that scripts check and turn into DDL and diagrams. The agent does the design; the scripts catch what a reviewer would catch and keep the artefacts consistent.

## Inputs

- `handoff/spec.md` (from `create-spec`), or any written specification. Data statements are `DM-nnn`; business rules `BR-nnn` often imply columns and constraints.
- `handoff/understanding.md` and `handoff/inventory.json` (from `understand-input`) for the data stores that exist today, including data kept only in browser storage.

## Steps

1. **List what must be stored.** Read the spec for nouns that persist (requests, customers, approvals, limits), the facts each carries, and the rules that constrain them. Read `references/spec-to-model.md` for how to turn statements into entities, attributes, enums and checks. Note the spec statement behind each choice.
2. **Draft `handoff/data-model/data-model.json`** following `assets/data-model.schema.json`. Look at `assets/examples/leave-request.data-model.json` for a complete worked example in a non-financial domain. Rules to follow (full list in `references/modeling-rules.md`):
   - one primary key per entity, usually a `uuid` generated by the database
   - exact types: money and quantities as `numeric(p,s)`, dates as `date`, instants as `timestamptz`, coded values as enums, never floats
   - every attribute carries `classification`, `personal_data`, and `protection`; Restricted data gets a protection method or a written note explaining the control
   - the entity classification is the highest of its attributes
   - audited entities set `audit: true` (the generator adds created and updated columns and an optimistic-locking `version`); include an `audit_log` entity for who, what, when, before and after
   - rules the database can enforce become constraints (`checks`, `unique`, foreign keys); the rule's spec id goes in `spec_refs`
   - reference data (limits, policies, allowances) is its own entity, not constants in code
   - `rls: true` for tables that hold per-user or per-role data (policies are designed with the service)
3. **Check it.**
   ```
   python3 scripts/validate_json.py assets/data-model.schema.json <handoff>/data-model/data-model.json
   python3 scripts/model_check.py --model <handoff>/data-model/data-model.json --spec-dir <handoff>
   ```
   Fix every error. Treat each warning as a question. The checker rejects float and money-as-integer mistakes, unknown enums, mismatched foreign-key types, personal data classified too low, Restricted data with no protection, and spec references that do not exist. It warns when a `DM-nnn` statement is not covered by any entity.
4. **Generate the artefacts.**
   ```
   python3 scripts/generate_ddl.py --model <handoff>/data-model/data-model.json --out <handoff>/data-model/schema.sql
   python3 scripts/generate_erd.py --model <handoff>/data-model/data-model.json --out <handoff>/data-model/erd.mmd
   ```
   Then the Flyway scripts, which are what a service actually runs:
   ```
   python3 scripts/generate_ddl.py --model <handoff>/data-model/data-model.json --flyway-dir <handoff>/data-model/migrations --tooling-dir <handoff>/data-model/flyway
   ```
   This writes one versioned script per concern, in dependency order: `V1__create_tables.sql` (structure), `V2__add_foreign_keys_and_indexes.sql`, `V3__table_and_column_comments.sql` (classification and protection notes for the data catalogue), `V4__row_level_security.sql`, and `V5__reference_data.sql` (seed rows for `reference_data` entities). `--tooling-dir` adds `flyway.conf` and `migrate.sh` for the Flyway command line; the connection comes from `FLYWAY_URL`, `FLYWAY_USER` and `FLYWAY_PASSWORD`, never from a file. Policies, view definitions and later changes are new versioned scripts that you add by hand; applied scripts are never edited. The SQL is generated, not executed: run it against a scratch PostgreSQL database before relying on it.
   Reference data (limits, allowances, lookup values the business owns) goes in the entity's `seed` rows; the checker validates every seed value against the types and enums.
5. **Note the migration** (when data exists today): in `handoff/data-model/migration-notes.md`, list what changes from the current data (type changes such as float to numeric or text to enum, NOT NULL columns that need a backfill, data that only lives in browsers) and the business decisions still open (how to map free-text values to enums, what to do with rows that break a new constraint).
6. **Gate: data owner review.** Show the person the ERD, the list of entities with classification and retention, and the open decisions. Ask the data owner to confirm retention periods, who may see Restricted columns, and the enum values. Record answers in `description`, `retention` and `protection_note`, then rerun the checks.

## Rules

- Never invent a business rule. If the spec does not say, put the question in the report and leave the constraint out, or add a check marked as proposed in its description.
- Do not model the screen. Model the facts and the rules.
- Keep names plain and snake_case; the schema rejects anything else. Avoid reserved words (`user`, `order`, `group`).
- Do not include real data, sample values from production, or secrets in the model.
- If the spec contradicts itself (two shapes for the same entity), list both and ask; do not pick silently.

## Output

`handoff/data-model/` with `data-model.json`, `schema.sql` (one file for review), `migrations/` (the Flyway scripts), `flyway/` (config and runner), `erd.mmd`, and `migration-notes.md`. The Java service skill reads `data-model.json` and the `migrations/` folder.

1. Propose it as a short list. For each item give the section affected, the exact change, and the reason (what it prevents next run).

3. Apply only the approved items to this `SKILL.md` (or its scripts, templates or references), keeping edits small. Tell the user what changed.
4. If nothing needs changing, say so in one line. Never record secrets, personal data or one-off project details as lessons.
